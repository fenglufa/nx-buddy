# 问题说明：桌面审图产品的"规则可被用户自行扩展"方案征询

> 目的：把背景和约束讲清楚，征求架构方案意见。可以整体转发。
> 一句话问题：**如何让机械设计团队在自己的机器上随时新增/修改图纸审核规则，而不需要软件厂商重新打包发版，同时不牺牲"规则没生效"这件事的可发现性和售后可控性。**

## 1. 产品与架构背景

- 产品：一款面向 NX（Siemens NX 2412）用户的商业闭源桌面套件（下称"本产品"），核心能力有二：
  1. **审图**：批量打开目录下的 *.prt 图纸，按公司标准逐条判定，产出 Excel 审图报告；
  2. **受守卫的建模**：通过 MCP（Model Context Protocol）stdio 服务向 AI Agent 暴露约 33 个建模/读图工具，AI 驱动的写操作（建孔、圆角、拉伸…）在提交进 NX 之前要先过同一套规则的"写前守卫"，违规直接拒绝并给修正建议（例如 φ13.2 的光孔不在标准直径系列 → 拒绝，建议 13 或 14）。
- 进程组成：
  - **NX 插件**（C#/.NET 4.8，NXOpen API，运行在 ugraf.exe 进程内）：唯一能真正读写 NX 模型的部件，负责"证据抽取"（打开图纸，提取孔/特征/图层/标题栏/尺寸等结构化数据）；
  - **MCP 宿主**（.NET 8 独立进程）：授权闸门、规则引擎、写前守卫、审图任务状态机；经命名管道与 NX 插件通信；
  - **托盘程序**（.NET 8 WinForms）：状态展示、规则管理页、审图工作台；同时是一个 MCP 客户端。
- 客户环境特点：单机授权（一机一 Key）、多数无外网、由 IT 统一装软件。

## 2. 现状：规则目前怎么定义、怎么生效

一份"规则"实际由三层拼成：

| 层 | 内容 | 现状载体 | 用户可改？ |
|---|---|---|---|
| 证据层 | 能从图纸/模型上观测到什么（孔径、螺纹标记、图框 id、标题栏字段、图层、板厚、孔组 PCD…） | NX 插件里的 C# 抽取代码，输出一个约 15 组强类型字段的封闭 JSON 证据模型 | 否 |
| 判定层 | 观测值与标准怎么比（∈系列、∈白名单、匹配正则、非空、计数≥4、双值+容差…） | **编译进引擎的约 23 个 C# 判定函数**，每条规则一个 switch 分支 | 否 |
| 参数/处置层 | 阈值表、系列表、白名单、级别（block/warn）、文案 | 随产品发布的只读规则包（JSON 数据目录，28 条规则+数值表） | 半是：已交付"用户覆盖层"（本机 JSON 文件），可禁用规则、整文件替换参数表，改后立即生效、带审计日志 |

即：**今天用户能调"规则的数值和开关"，不能增删"规则本身"，因为判定逻辑是编译代码**。

## 3. 问题

1. 客户标准在早期会高频演进（新增判定项、调整口径），每次都要厂商改代码→重新打包→逐机升级，商业上不可持续；
2. 反过来，如果把口子完全开死，产品卖不动——客户采购时明确把"标准可自维护"当作条件；
3. 还有一个容易被忽视的负面：**"加了规则但没触发"比"不能加规则"更危险**——审图漏报的代价是图纸事故。任何自服务方案必须让"这条规则到底怎么判的、会命中什么"可验证、可发现。

## 4. 需求与约束

必选：
- R1 用户可在工作站上**新增/编辑/停用/删除整条规则**，不需要重启、不需要厂商发版；
- R2 同一套规则定义要同时驱动**审图（存量批量判定）**与**写前守卫（增量单次判定）**两条链路，不允许两套逻辑打架；
- R3 规则是纯数据：不得引入可执行代码注入面（本产品同时被 AI Agent 调用，规则文件也可能被非 programmer 的工艺工程师编辑）；
- R4 闭源商业产品：方案不能要求开放源码或把引擎逻辑交给客户；
- R5 升级安全：产品版本升级不得悄悄破坏或重置用户的自定义规则（当前用户状态与只读规则包分离存放，已是如此）；
- R6 离线环境可用（无云端规则库、无在线校验服务可依赖）。

倾向：
- S1 规则能在多台机器间导出/导入（IT 统一分发，或厂商远程替客户调试后回传）；
- S2 新增规则前能**试跑**：拿历史审图数据 dry-run，展示"这条规则会命中哪些对象、报什么"；
- S3 编辑界面面向工艺工程师（表单/下拉），不要求手写 JSON。

开放问题：
- O1 表达力上限：存在跨对象聚合类判定（"同直径独立孔≥4 个应改用阵列"）、几何计算类（孔组 PCD 容差、板厚启发）。哪些必须保留在编译层是合理边界？
- O2 若部分复杂规则需要脚本表达，沙箱脚本（如 Jint/Lua）的售后与安全成本是否值得？还是宁可把这类需求划归"厂商版本扩展"？

## 5. 已有候选思路（供批评，非决定）

- **A 纯声明式条件语言**：规则=JSON（选对象类型 → 取字段 → 与阈值/系列表/白名单/正则比对，支持 all/any/count/tolerance 等聚合原语）；引擎内置通用评估器；装载时 schema 校验，非法规则 fail-closed 并明确报错。按现有 23 个判定函数归约，估计 8–10 个原语可覆盖绝大多数。缺点：表达力有上限，上限之外仍需发版。
- **B 内嵌脚本引擎**：表达力无限，但安全面、调试、假阴性售后责任问题严重，与 R3 冲突。倾向仅作为远期企业版逃生舱。
- **C 分层混合（当前倾向）**：数据档（已有覆盖层）+ 规则档（A 的声明式规则存"用户规则包"目录，随编辑器+dry-run 交付）+ 引擎档（新观测项、新原语仍走厂商发版）。配套的关键改造是**证据层开放**：把证据模型从 15 字段封闭集改为"自描述字段目录"（对象类型→字段→单位→示例），规则编辑器下拉直接吃这份目录，让"新规则=已有字段的重新组合"成为常态。
- 未决的重分配：客户想查一个从未抽取过的观测量（如表面粗糙度符号）时，成本落在一期抽取层的通用化（尽量把 NX 对象属性/用户属性泛化导出，让"新观测"降级为"选字段"），还是仍接受这类需求走版本排期？

## 6. 想征求的具体意见

1. 分层边界画得对不对？"引擎档"应该保留多大比例？
2. 声明式条件语言如果要做，语法形态怎么选（JSON 组合器 / 表达式 mini-language / 复用现成策略语言如 JSON Logic、CEL），校验与假阴性防线怎么设计？
3. 审图（批量、事后）与写前守卫（单次、事前）共用一套规则定义的方案有无坑？
4. 面向非程序员（工艺工程师）的规则编辑器 + dry-run，产品形态上有什么成熟参照或教训？
5. 闭源桌面软件 + 客户自改规则，责任划分（谁的规则谁负责）在合同/日志/版本快照上怎么落比较稳？
